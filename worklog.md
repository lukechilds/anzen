# Implementation worklog

This file records implementation decisions and unforeseen constraints that were not fully specified in `vault-design.md`.

## 2026-08-03

- Use the current modular BDK crates (`bdk_wallet` 3.1 and `bdk_bitcoind_rpc` 0.22) rather than the deprecated monolithic `bdk` crate. The versions are pinned in `Cargo.lock` for reproducible builds.
- Use BIP86 Taproot external/change descriptors for the ordinary mobile hot wallet. The vault itself uses the custom static Taproot descriptor from the design and is tracked separately because its UTXOs require explicit script-path and batch-presigning behavior.
- Use the standard BIP341 NUMS point as the static Taproot internal key. This makes the descriptor deterministic and recoverable without extra state.
- Derive the static phone and HWW vault signing keys from a dedicated path, separate from the phone hot-wallet account. Regtest uses BIP coin type 1 and mainnet uses coin type 0. Encryption keys are domain-separated from signing keys with HKDF-SHA256.
- Store protocol metadata as human-readable JSON and BDK hot-wallet chain state in SQLite. Device secrets and encrypted artifacts are separate files so loss/theft scenarios can remove or copy realistic subsets of state.
- The simulated HWW encrypts the phone mnemonic with a symmetric key derived from the HWW seed. A production HWW integration will need a device-defined authenticated encryption/decryption API; the MVP deliberately models the capability without claiming compatibility with an existing device.
- Synchronize the ranged phone hot wallet through BDK's Bitcoin Core emitter and persist its chain graph in SQLite. Discover static vault UTXOs with Bitcoin Core's `scantxoutset` RPC. This avoids importing private keys or making the node wallet part of the vault security model while still validating all transactions against a real node.
- Keep the Bitcoin Core RPC client regtest-only and fail closed if Core reports any other network. Mainnet uses a separate Electrum backend. The CLI exposes mock-time and on-demand mining controls solely to support the Dockerized regtest demonstration.
- Populate standard Taproot PSBT fields from the full static Miniscript descriptor and use `SIGHASH_DEFAULT`, so every signature commits to all transaction inputs and outputs. The simulated phone and HWW sign only the explicitly selected cooperative or recovery leaf; Miniscript performs final witness construction. A live Bitcoin Core regtest acceptance test verifies the resulting cooperative script-path witness.
- Require every funded monthly chunk to leave a non-dust cold remainder after releasing the approved monthly limit and paying its parent fee. If the entire balance cannot satisfy that for twelve chunks, reduce the funded month count as specified. A balance too small for one full authorization is rejected rather than creating a rollover with no usable monthly authorization.
- For a positive soft limit, return exactly `monthly limit - soft limit` to the vault and pay the child fee from the hot remainder. For a zero soft limit, no hot remainder exists, so return the entire authorization output minus the child fee to the vault. If soft equals the monthly limit, no child transaction is necessary.
- Recovery sweeps use only confirmed vault UTXOs that are mature for the selected CSV path. If vault outputs have different confirmation heights, mature outputs can be recovered while newer outputs remain for a later sweep.
- Emergency phone-key rotation generates a new phone vault key, new BIP86 hot-wallet account, new static vault address, and new HWW-encrypted phone backup. It archives old public configuration and obsolete presigned ciphertext/BDK state, but deliberately does not retain another plaintext copy of the compromised phone mnemonic. Spending the old outputs invalidates their presigned monthly transactions; when a monthly limit is active, the same rotation package chains a fresh 12-month schedule at that limit to the sweep and encrypts it to the new phone key.
- The MVP treats successful mempool acceptance as the emergency-rotation state boundary. Production must make rotation state updates crash-safe and track confirmation/rebroadcast or rollback if the sweep is later evicted.
- Recovery integration tests mine the real 61,200/65,535-block CSV delays in bounded 5,000-block RPC batches, use a five-minute RPC timeout, and advance regtest mock time between batches. Core can legitimately take longer than the JSON-RPC library's 15-second default, while tens of thousands of rapidly generated blocks otherwise eventually violate Core's two-hour future-timestamp rule. Mock time only keeps block timestamps valid; the test still mines every block required by CSV.
- Docker pins the official `bitcoin/bitcoin:28.1` image and Rust 1.85 builder. Each narrative runner invocation creates a uniquely named Compose project and destroys only that project's disposable containers/volumes before and after each run. This preserves the height-zero chain and early regtest subsidy assumptions without allowing concurrent local runs to tear one another down.
- Split the narrative demo into selectable, isolated end-to-end tests. The host runner executes selected tests serially and resets Bitcoin Core before each one; this keeps setup adjacent to the behavior under test, makes every test independently reproducible, and avoids depending on block subsidy after a 65,535-block recovery run. Long mining is still performed in timestamp-safe 5,000-block batches, but the internal batches and mock-time updates are hidden behind one CLI action and a compact progress indicator.
- GitHub Actions runs Rust quality/unit checks, the existing Dockerized real-node suite, and all named end-to-end tests on pushes and pull requests. E2E tests stay serial within one job so the demo image is built once and each test uses the runner's explicit fresh-chain boundary; the job has a larger timeout, and branch-level concurrency cancels superseded recovery runs.
- Cache direct Cargo builds with `actions/cache`, and build the Docker `test` and `runtime` targets with Buildx's GHA backend in separate scopes. CI loads those tagged images into Docker and explicitly skips the scripts' normal Compose build, while local invocations keep their existing build behavior. The Dockerfile precompiles release and test dependencies before application source is copied so a source edit does not invalidate the expensive dependency layer.
- Model an on-time annual rollover as 52,560 real blocks (365 days at 144 blocks/day) plus calendar MTP advancement. The end-to-end test renews all twelve unused chunks before either recovery path activates, verifies the confirmation-height-based timers reset, proves the old monthly authorizations conflict with the confirmed rollover, and advances to the old phone-recovery deadline to prove it no longer applies to the renewed outputs.
- Separate simulated device actions at the CLI boundary. Phone operations are under `vault phone *`, HWW operations are under `vault hww *`, and vault construction requires explicit phone, HWW, then vault initialization. Initialization creates the static cold policy with a zero monthly limit; it does not presign spending transactions.
- Exchange policy, cooperative-sweep, backup-recovery, and phone-rotation state as versioned JSON objects. Policy objects embed the manifest and every PSBT, eliminating an implicit shared ceremony directory while allowing each device stage to validate what it received.
- Use a three-stage monthly policy protocol: the phone proposes and signs, the HWW displays one high-level approval and validates/signs the entire batch, then the phone verifies, broadcasts, and activates it. A zero-limit policy makes one cold rollover output and no monthly transaction pairs.
- Use a three-stage emergency phone-key rotation protocol with a phone proposal, HWW validation/signature plus replacement backup encryption, and phone activation. If monthly spending is active, the proposal also includes a replacement annual policy rollover chained to the rotation sweep, so one HWW approval signs the sweep and replacement schedule. The software-HWW simulation reads the locally pending replacement phone key to model a future authenticated device channel; production hardware integration must replace this with an explicit secure backup-encryption capability.
- Treat delayed phone-only or HWW-only recovery to a newly initialized replacement vault as full key rotation after permanent counterpart loss. This intentionally replaces both simulated device epochs; preserving the surviving device key during a one-sided delayed rotation is not required for the MVP.
- Keep regtest as the default but permit an explicitly danger-gated mainnet configuration. Mainnet must be selected when the first simulated device is initialized, is persisted in device and vault state, uses BIP86 coin type 0, and requires `--dangerously-enable-mainnet` again before every later command. The flag cannot convert an existing regtest vault.
- Use Bitcoin Core RPC only for regtest and BDK Electrum for mainnet. Mainnet attempts a fixed list of public TLS servers in order and rejects any server whose genesis header is not Bitcoin mainnet. This failover list is an MVP availability convenience, not a privacy or trust boundary; production should use a configurable, preferably user-owned backend.
- Enforce a one-way library dependency graph: `hot_wallet -> core` and `cold_wallet -> core`, with no dependency between device implementations and no device dependency from `core`. Shared policy/PSBT rules and protocol objects remain in `core`; BDK state, phone encryption, and rotation activation live in `hot_wallet`; HWW review, backup encryption, and signing loops live visibly in `cold_wallet`.
- Keep HWW recovery signing offline. The CLI obtains the chain tip and confirmed vault UTXOs through `core`, passes only that explicit data to `cold_wallet`, and broadcasts the returned signed transaction itself. Architecture tests reject hot/cold cross-imports, device imports from production `core`, and CLI dispatch that bypasses the appropriate device library.
